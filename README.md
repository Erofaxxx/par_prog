# Yandex Metrica Reports API (Stat API) — документация для универсального ИИ‑аналитика

Цель: по этой документации можно реализовать агента, который **регулярно выгружает набор “ядровых” отчётов** из Яндекс Метрики через API, **адаптируется** к тому, какие данные реально есть в счётчике (цели, e‑commerce, расходы, UTM), и на их основе генерирует **действия для оптимизации рекламных кампаний**.

Фокус: **Reports API / Stat API** (агрегированные отчёты). Logs API подключайте опционально для точечного расследования (путь пользователя, сырые события, антифрод).

---

## 1) Термины и подход

### 1.1) Два режима работы агента

1) **KPI‑режим (основной)**: агрегаты по источникам/кампаниям/лендингам/устройствам/гео/времени. Делает 80% полезных выводов и проще в эксплуатации.
2) **Forensics‑режим (опционально)**: сырые визиты/хиты (Logs API) для точечных вопросов (“почему выросли отказы у кампании X?”, “какие шаги до заявки?”).

### 1.2) Что значит “оптимизация рекламы” без Директа и без расходов

Если в Метрике **нет данных о расходах**, агент всё равно может оптимизировать:
- качество трафика и конверсию (CR) по UTM‑кампаниям и лендингам,
- сегменты с провалами (мобайл/гео/время),
- устойчивость воронки (микро‑цели vs макро‑цели),
- а когда расходы появятся (загрузка/интеграции) — добавит CPA/ROI.

## 2) Авторизация и базовые URL

### 2.1) Авторизация

Используется OAuth‑токен Яндекса в заголовке:

```text
Authorization: OAuth <token>
```

### 2.2) Базовые URL

- Management API (счётчики, цели, доступ): `https://api-metrika.yandex.net/management/v1/`
- Stat API / Reports API (отчёты): `https://api-metrika.yandex.net/stat/v1/`

## 3) Инвентаризация (обязательная для адаптивности)

Агент должен начинать не с “жёстко заданных” запросов, а с диагностики: что реально доступно в счётчике.

### 3.1) Список целей

Нужно получить:
- `goal_id` (для параметризованных метрик),
- тип цели (заявка/событие/страница и т. п.),
- признак “основная/вспомогательная” (агент может выводить сам, см. 6.1).

Результат: список `goal_ids[]`.

Рекомендуемый вызов (Management API):
- `GET /management/v1/counter/<counter_id>/goals`

### 3.2) Metadata (что доступно в Stat API)

Нужно запросить metadata и построить локальный справочник:
- `dimensions` (какие измерения есть),
- `metrics` (какие метрики есть),
- какие комбинации поддерживаются (важно для предотвращения 400 ошибок),
- какие группы относятся к визитам (`ym:s:*`) и хитам (`ym:pv:*`) и не смешиваются.

Результат: `capabilities.json` (в памяти/кэше), например:
- `has_utm` (есть UTM‑измерения и они не пустые),
- `has_ecommerce` (есть ecommerce‑метрики и они не пустые),
- `has_costs` (есть расходные метрики и они не пустые),
- `has_calltracking` (если используете офлайн‑звонки/конверсии — опционально).

### 3.3) “Probe queries” (быстрая проверка на непустые данные)

Metadata говорит “доступно”, но не говорит “заполнено”.
Сделайте 3–5 быстрых запросов на последние 7 дней с маленьким `limit`:
- UTM: есть ли хотя бы 1 строка, где `ym:s:UTMCampaign` (или эквивалент из metadata) не пустой.
- Ecommerce: есть ли заказы/доход.
- Расходы: есть ли ненулевые расходные метрики (если вы их загружаете/интегрируете).
- Цели: есть ли конверсии по целям.

Результат: `data_presence` (булевы флаги + объёмы).

## 4) Stat API: как устроены запросы к отчётам

### 4.1) Главные эндпоинты

- `GET /stat/v1/data` — агрегированный отчёт.
- `GET /stat/v1/data/bytime` — то же, но с разбиением по времени (тренды).
- `GET /stat/v1/metadata` — справочник измерений/метрик и совместимости.

### 4.2) Каркас запроса `/stat/v1/data`

Минимально:
- `ids`: ID счётчика
- `date1`, `date2`: даты `YYYY-MM-DD`
- `dimensions`: список измерений через запятую
- `metrics`: список метрик через запятую

Часто нужно:
- `filters`: сегментация
- `sort`: сортировка
- `limit`, `offset`: пагинация
- `accuracy`, `proposed_accuracy`: контроль семплинга
- `attribution`: модель атрибуции

### 4.3) Важные ограничения, которые должен учитывать агент

- **Нельзя смешивать префиксы** визитов и хитов в одном отчёте: условно `ym:s:*` отдельно от `ym:pv:*`.
- Многие “тонкие” разрезы приводят к семплингу; агент обязан учитывать `sample_share` и снижать уверенность выводов.
- В ответе может быть `contains_sensitive_data=true`; агент не должен пытаться “достроить” скрытые значения.

### 4.4) Пагинация

Агент должен уметь выкачивать отчёт постранично:
- `limit` (например, 10k–100k в зависимости от практики)
- `offset` (1‑based)

Если итоговая строк больше лимита — выгружать до конца.

### 4.5) `bytime` для трендов

`/stat/v1/data/bytime` используйте для:
- динамики по дням/неделям,
- обнаружения просадок после изменений,
- сезонности.

Данные в `bytime` приходят “сериями” по времени; для агрегации их нужно привести к табличному виду:
`dimensions + time_bucket + metrics`.

### 4.6) Слой абстракции: “логические поля” → реальные ID

Чтобы агент был универсальным, удобно внутри кода оперировать “логическими” полями (например, `utm_campaign`, `landing_path`, `device`), а перед запросом маппить их на **реальные ID** из `/stat/v1/metadata`.

Пример типовых real‑ID (всегда проверяйте через metadata, т. к. набор может отличаться):
- UTM: `ym:s:UTMSource`, `ym:s:UTMMedium`, `ym:s:UTMCampaign`, `ym:s:UTMContent`, `ym:s:UTMTerm`
- Лендинг: `ym:s:startURL`, `ym:s:startURLPath`, `ym:s:startURLPathLevel1`, `ym:s:startURLPathLevel2`
- Время: `ym:s:date` (для `/data`) или `bytime` (для `/data/bytime`)

Правило: если в metadata нет поля — агент должен либо выбрать альтернативу (например, более агрегированный уровень), либо выключить соответствующий отчёт.

### 4.7) Формат ответа `/stat/v1/data` (что парсить в агенте)

Критичные поля ответа, на которые обычно опирается агент:
- `data`: массив строк; каждая строка содержит `dimensions[]` (значения разрезов) и `metrics[]` (числа).
- `totals`: итоги по метрикам (полезно для долей/контроля).
- `query`: отражает параметры запроса (удобно сохранять рядом с выгрузкой).
- `sample_share`/`sample_size`/`sample_space`: индикаторы семплинга (используйте для “уверенности” выводов).
- `contains_sensitive_data`: флаг, что часть данных скрыта/агрегирована по правилам приватности.

Практика: сохраняйте исходный ответ JSON (или минимум `query`, `sample_share`, `data`) рядом с таблицей, чтобы уметь воспроизводить выводы.

### 4.8) `filters` и `sort` (практические правила)

- Синтаксис `filters` — строковое выражение. Агент должен держать библиотеку “шаблонов фильтров” (например, paid‑traffic по `UTMMedium`) и включать их только если измерения существуют (через metadata).
- `sort` используйте, чтобы получать top‑N без выкачивания всего (например, сортировка по визитам/конверсиям).
- При 400 ошибках из‑за несовместимости измерений/метрик — пересобирайте запрос на основе metadata (см. 9).

## 5) “Ядро запросов” (универсальный набор)

Ниже — минимальный набор отчётов, который почти всегда полезен. Агент должен:
1) выполнить их по умолчанию,
2) адаптировать список измерений/метрик в зависимости от `capabilities` и `data_presence`,
3) генерировать выводы и действия (см. 7).

Во всех запросах:
- период: последние 7/14/28 дней (агент выбирает, но минимум 7)
- `accuracy=high`, `proposed_accuracy=true`
- `attribution` фиксирован (например, `lastsign`) для сопоставимости

### 5.1) Q1 — Performance по UTM‑кампаниям (основной “скелет”)

Назначение: что масштабировать/резать по конверсиям и качеству.

Измерения (если есть UTM).
Важно: в запросах используйте **точные ID измерений** из `/stat/v1/metadata` (обычно это `ym:s:UTMSource`, `ym:s:UTMMedium`, `ym:s:UTMCampaign`, …):
- `ym:s:UTMSource`, `ym:s:UTMMedium`, `ym:s:UTMCampaign`
- опционально: `ym:s:UTMContent`, `ym:s:UTMTerm` (если объёма хватает)

Метрики (минимум):
- визиты, пользователи
- конверсии по 1–3 primary‑целям (см. 6.1)
- если ecommerce: заказы/доход
- если расходы: adcost + производные (CPC/CPA/ROI)

### 5.2) Q2 — Кампания × Лендинг (startURL)

Назначение: находить лендинги, которые “ломают” конверсию.

Измерения:
- `ym:s:UTMCampaign` (или полный UTM‑набор)
- входная страница: обычно `ym:s:startURLPath` или `ym:s:startURL` (агент выбирает по кардинальности)

Метрики:
- визиты
- CR и/или конверсии primary‑цели
- отказы / вовлечённость (как диагностические метрики)
- ecommerce/расходы — если есть

### 5.3) Q3 — Кампания × Устройство/платформа

Назначение: корректировки по мобайлу/десктопу, iOS/Android, браузерам.

Измерения:
- `ym:s:UTMCampaign`
- измерение устройства (например, `ym:s:deviceCategory` или аналог в metadata)
- опционально: ОС/браузер (ID — через metadata)

Метрики:
- визиты
- конверсии/CR primary‑цели

### 5.4) Q4 — Кампания × Гео

Назначение: гео‑оптимизация (исключения/расширения, отдельные офферы).

Измерения:
- `ym:s:UTMCampaign`
- измерение гео (например, `ym:s:regionCity` или более агрегированное — ID через metadata)

Метрики:
- визиты
- конверсии/CR primary‑цели

### 5.5) Q5 — Тренд по времени (bytime) для топ‑кампаний

Назначение: выявлять просадки и эффект изменений.

Подход:
- сначала определить топ‑N кампаний по визитам/конверсиям из Q1
- затем для каждой кампании (или батчами) запросить `bytime` по дням

Измерения:
- `ym:s:UTMCampaign` (или `ym:s:UTMCampaign,ym:s:UTMSource`)

Метрики:
- визиты
- конверсии primary‑цели
- ecommerce/расходы — если есть

### 5.6) Q6 — Качество трафика (fallback, когда конверсий мало)

Назначение: если primary‑конверсий мало или ноль, агент временно оптимизирует прокси‑метрики.

Измерения:
- `ym:s:UTMSource`/`ym:s:UTMMedium`/`ym:s:UTMCampaign`

Метрики (примерно):
- отказы
- глубина/время
- доля новых пользователей

Важно: агент должен помечать, что это “прокси”, и предлагать улучшить трекинг (добавить цели, ecommerce, офлайн‑конверсии).

## 6) Адаптивность: как агент выбирает цели, метрики, разрезы

### 6.1) Выбор “основных” конверсий

Алгоритм (практичный, без доменной магии):
1) Если ecommerce‑метрики присутствуют и ненулевые: primary KPI = доход/заказы.
2) Иначе: кандидаты = все цели.
3) Для каждой цели за последние 28 дней оценить:
   - объём (конверсии),
   - стабильность (сколько дней с ненулевым значением),
   - “информативность” (не слишком ли цель микро‑уровня).
4) Выбрать 1–3 цели как primary:
   - 1 “макро” (заявка/покупка), если объём достаточный,
   - 1–2 “микро” (добавление в корзину/клик по кнопке), если макро‑объёма мало.

Технически: метрики по целям в Stat API обычно параметризованы и содержат `goal_id` в имени (вид вроде `ym:s:goal<goal_id>...`). Агент должен получать доступный список таких метрик через `/stat/v1/metadata` и собирать их по найденным `goal_ids`.

### 6.2) Автовыбор разрезов по кардинальности

Проблема: `startURL` и `UTMContent` могут дать сотни тысяч значений → семплинг/лимиты.

Решение:
- сначала проба на 7 дней с `limit=1000`
- если уникальных значений слишком много:
  - заменить `ym:s:startURL` на `ym:s:startURLPath` или `ym:s:startURLPathLevel1/2`
  - заменить `ym:s:UTMContent` на “топ‑креативы” (ограничить фильтром `IN` по top‑N)

### 6.3) Детект наличия расходов

Агент должен работать в 3 режимах:
- `no_costs`: расходов нет → рекомендации по CR/качеству
- `costs_present`: расходы есть → CPA/ROI/scale/stop
- `unknown`: метрика доступна, но все нули → считать как `no_costs` и поставить задачу на проверку интеграции

### 6.4) Сегментация (filters) как “универсальный рычаг”

Типовые сегменты, которые агент может применять:
- только платный трафик (по UTM medium, например `cpc/paid`)
- исключение внутренних переходов/тестов (по IP/UTM‑меткам, если заведены)
- новые vs возвратные пользователи

Правило: перед применением фильтра агент должен проверить, что соответствующее измерение доступно (через metadata).

## 7) Какие выводы и действия генерировать из каждого ядрового отчёта

Это важно: агент не просто “анализирует таблицы”, а возвращает **действия**.

### 7.1) Из Q1 (UTM performance)

Действия:
- “Масштабировать”: кампании с высоким CR/выручкой и достаточным объёмом.
- “Остановить/урезать”: кампании с большим объёмом визитов и нулём primary‑конверсий (с учётом доверительных порогов).
- “Ресегментировать”: выделить успешные `source/medium` внутри кампании.
- “Проверить трекинг”: если трафик есть, а конверсии везде ноль.

### 7.2) Из Q2 (кампания × лендинг)

Действия:
- “Перелить трафик” на лендинги с лучшим CR.
- “Починить лендинг”: страницы с высоким трафиком и провалом CR/отказами.
- “Уточнить соответствие”: кампании, ведущие на нерелевантные страницы (разный интент).

### 7.3) Из Q3/Q4 (устройство/гео)

Действия:
- “Корректировки ставок/таргета”: сегменты с системно низким CR.
- “Отдельные кампании/креативы”: если сегмент большой и отличается по поведению.

### 7.4) Из Q5 (тренды)

Действия:
- “Аномалия”: резкое падение CR/конверсий при стабильном трафике.
- “Эффект изменения”: сравнение до/после по дням (агент должен уметь делать контрольные окна).

---

## 8) Надёжность: семплинг, пороги, статистика

### 8.1) Семплинг

Если `sample_share` низкий:
- агент понижает уверенность выводов,
- пытается увеличить точность (`accuracy=full` или выше, если возможно),
- уменьшает кардинальность разрезов (агрегирует URL/контент/терм).

### 8.2) Минимальные пороги для “режущих” рекомендаций

Чтобы не резать на шуме, используйте пороги:
- минимум визитов (например, 200–500) прежде чем делать жёсткий вывод
- минимум времени наблюдения (например, 7 дней)
- при наличии расходов: минимум затрат (если есть)

Пороги должны быть настраиваемыми.

---

## 9) Ошибки и ретраи

Агент должен:
- логировать `request_id`, параметры, HTTP‑код, тело ошибки,
- ретраить 429/503 с backoff,
- на 400 (несовместимые dims/metrics) автоматически пересобрать запрос через metadata:
  - убрать конфликтующий параметр,
  - или разбить на два запроса (например, визиты vs хиты).

## 10) Python: рекомендуемая структура клиента (без привязки к фреймворку)

Минимальные компоненты:
- `MetrikaClient`: HTTP, авторизация, ретраи, rate‑limit.
- `MetadataCache`: загрузка/кэш metadata + проверка доступности измерений/метрик.
- `Inventory`: цели, ecommerce/costs presence.
- `QueryBuilder`: сборка запросов из “шаблонов” + адаптация.
- `Extractor`: пагинация, сохранение таблиц (CSV/Parquet), контроль схемы.
- `Analyzer`: вычисление KPI, аномалии, рекомендации.

Рекомендуемые практики выгрузки:
- сохранять “сырые” выгрузки с именованием: `report_<name>_<counter>_<date1>_<date2>.parquet`
- сохранять `query.json` рядом (для воспроизводимости)
- нормализовать столбцы (snake_case) и типы

### 10.1) Минимальный пример вызова Stat API (requests)

```python
import time
from typing import Any

import requests

BASE_STAT = "https://api-metrika.yandex.net/stat/v1"


def _headers(token: str) -> dict[str, str]:
    return {"Authorization": f"OAuth {token}"}


def stat_metadata(token: str) -> dict[str, Any]:
    r = requests.get(f"{BASE_STAT}/metadata", headers=_headers(token), timeout=60)
    r.raise_for_status()
    return r.json()


def stat_data_all_pages(token: str, params: dict[str, Any], limit: int = 10000) -> list[dict[str, Any]]:
    # Возвращает "сырые" строки `data` (dimensions+metrics). Табличный вид строится отдельно.
    rows: list[dict[str, Any]] = []
    offset = 1
    while True:
        page_params = dict(params)
        page_params["limit"] = limit
        page_params["offset"] = offset
        r = requests.get(f"{BASE_STAT}/data", headers=_headers(token), params=page_params, timeout=120)
        if r.status_code in (429, 503):
            time.sleep(2)
            continue
        r.raise_for_status()
        payload = r.json()
        data = payload.get("data", [])
        rows.extend(data)
        if len(data) < limit:
            break
        offset += limit
    return rows
```

## 11) Минимальная конфигурация агента (что вводит человек)

Чтобы агент был универсальным, конфиг должен быть коротким:
- `counter_id`
- `timezone` (если нужно)
- `primary_goal_ids` (опционально; если не задано — агент выбирает сам)
- `paid_mediums` (опционально; список вроде `["cpc","paid"]`)
- `internal_utm_markers` (опционально)
- пороги (минимум визитов, минимум дней)

Всё остальное (наличие UTM, ecommerce, расходов) агент определяет сам.
